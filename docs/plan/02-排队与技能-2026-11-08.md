## 0. 作用域：一个会话 = 一个项目

用户已定。**跟着会话走。**

| 东西 | 作用域 | 理由 |
|---|---|---|
| 台面（任务 / 卡片 / 图墙） | **每会话一份** | 一个会话就是一个项目；侧栏只显示本会话的卡 |
| `LovartMeta` | 带 `sessionId` | 没有它就没法过滤（现在就是全局的，跨会话串台） |
| 队列与槽位 | **全局一份** | 槽位是 Lovart **账号级**的，不是会话级的；A 会话提满 4 个，B 会话也得等 |
| 落盘目录 | 每会话一份（`<cwd>/lovart/`） | cwd 本来就是会话的 |
| AI 视角 | 与台面一致 | DSH 的 `job_list` 本来就按会话，终于对上了 |

队列全局、台面分会话，这两条不矛盾：**「谁能看见」按会话，「谁能占槽」按账号。**

**假设：同一时间只有一个会话在用这个插件。** 用户不会开多个会话各提一堆图，所以：

- **不做全局容量数字**，也不做「其中 N 个来自其他会话」这种跨会话提示。
- 侧栏的 `运行 2/4` 就按**本会话**数：`jobs.filter(j => j.holdsSlot).length` / `options.maxConcurrency`。
- 真出现两个会话同时用，队列仍然正确（按账号排队），只是各自看到的 `2/4` 都只是自己那一份——这是已知且接受的偏差。

## 1. 为什么要改

现在的规则是「并发满了直接拒绝」（00 §5.6）：

```
active + requested > maxConcurrency  ⇒  409「并发已满：4/4，本次请求 1 个」
```

用户说「做 4 张《小猫钓鱼》，再做 2 张《小马过河》」时，第二次调用必然失败：

| 步骤 | 现状 |
|---|---|
| `count:4` | 4 个 job，占满 4 槽 |
| `count:2` | `4 + 2 > 4` ⇒ 409 |
| 4 张跑完 | 模型被通知 4 次，但**没有任何东西提醒它还有 2 张没提** |
| 结果 | 出来 4 张，2 张丢了 |

这不是模型笨，是设计里没有「待提交」这个状态。**结论：把「拒绝」换成「排队」。**

这同时推翻了 00 §1.2 的「不做并发槽位账」与 §5.6 的「不排队、不重投」。
按 AGENTS §6.1，落地时新增 ADR-0010，记录「为什么从拒绝改为排队」。

## 2. 参考实现怎么排（只取我们需要的部分）

`lovart 自动` 的做法，三条值得抄：

1. **状态是唯一真源，槽位从状态派生。** `state.rs` 的 `TaskStatus`（`Pending` / `Submitting` / `Running` / …）配一张登记表，`holds_slot(status)` 直接查表；
   注释写明「槽位计数由它派生，**不另立计数器**」——计数器会和真相漂移。
2. **「已认领、正在提交」是显式状态**（`Submitting`），所以不需要「预占 +1 / 归还 -1」。
3. **未开始的任务是 `Pending`**，在队列里等，不占槽；看板上它属于 `queued` 组。

不抄的部分：`Timeout` / `Unresolved` / `DownloadFailed` 这些断点续跑状态（我们不落盘、不续跑）、
`NeedsConfirm` 的自动确认（我们永远只让人确认）。

## 3. 目标与非目标

**做**

- 提交永不因为并发被拒；超出的任务进本地队列。
- 队列状态可见（侧栏徽章 + 会话头进度行）。
- 取消排队中的任务，等于没提交过。
- 给 agent 一个必选 skill，写明「lovart 作图」怎么开工。

**不做**

- 不做断点续跑、不落盘队列状态（重启即丢，与 00 §C6 一致）。
- 不做 402 熔断、不做超时释放。
- 不做服务端槽位探测（我们只知道本地在跑几个）。

## 4. 数据形状

### 4.1 Phase 表加一行（00 §4.2）

| phase | 含义 | 占槽 | `JobView.status` | 进度行 | 徽章 |
|---|---|---|---|---|---|
| `waiting` | **本地等空位，还没提交上游** | ❌ | `running` | `等待空位` | `等待中` |
| `submitting` | 设模式 + 建项目 + 发 chat | ✅ | `running` | `提交中` | `提交中` |
| `downloading` | 已出图，正在下载 | **❌（改）** | `running` | `下载中` | `下载中` |

其余六行不变。`waiting` 与 `queued` 是两件事：`queued` 是**上游**排队，`waiting` 是**本地**没轮到。

`downloading` 从 ✅ 改 ❌：上游此时已经 `done`，槽位是上游的，本地下载不该继续挡着队列。

### 4.2 槽位队列

```ts
/** 一次 apply 一份；不导出实例、不落全局（ADR-0009 第一级）。 */
export interface SlotQueue {
  /** 领号：有空位立即拿到，否则排队；返回的 promise 只 resolve 一次。 */
  take(): SlotTicket
}

export interface SlotTicket {
  /** true = 拿到槽位；false = 等待期间被取消。 */
  readonly granted: Promise<boolean>
  /** 取消等待：还在队列里就摘掉并 resolve(false)；已拿到则无效。 */
  cancel(): void
  /** 还槽并唤醒下一个；拿到过才需要调用，重复调用无效。 */
  release(): void
}
```

**不对外提供「当前占用数」**：占槽与否由 phase 派生（`PHASE_TABLE[phase].holdsSlot`），
侧栏要显示 `运行 2/4` 时，由 host 在 `JobView` 上派生 `holdsSlot`，client 数一遍即可。
队列自己只回答「能不能拿到」，不回答「现在几个」——两个问题会漂移。

### 4.3 LovartMeta

`waiting` 是 `phase` 的一个值，不新增阶段字段；**但要新增 `sessionId`**（见 §0）：

```ts
interface LovartMeta {
  // …其余不变
  /** 归属会话。一个会话 = 一个项目，台面按它过滤。 */
  readonly sessionId: string
}
```

现在这份数据**没有 `sessionId`**，所以 `GET /lovart/api/jobs` 返回的是整个 store ——
会话 A 的图会出现在会话 B 的侧栏里。这是必须先修的 bug（P3-0），与排队无关。

## 5. 数据流

```
提交（工具 / 侧栏）
   → ctx.jobs.start() 立即发放 jobId（不变）
   → phase = waiting，进度「等待空位」
   → const ticket = queue.take()
   → await ticket.granted
        ├─ false（等的时候被取消） → 终态 cancelled，不还槽（没拿到）
        └─ true                     → 下面整段包在 try/finally 里
                                       try  { 提交 → 轮询 → 下载 → done }
                                       finally { ticket.release() }   ← 唤醒下一个
```

规则：

1. **取消**：`hooks.cancel()` 同时做三件事——`ticket.cancel()`、`unblockConfirm?.()`、`wake?.()`。
2. **还槽时机**：`finally`，覆盖成功 / 失败 / 取消三条路径，只还一次。
3. **确认不占槽**：`confirming` 仍 `holdsSlot: false`，不改变。
4. **顺序**：FIFO，按 `createdAt`（同一毫秒按入队顺序）。
5. **队列无上限**：用户一次提 20 张就排 20 张；不做「队列满拒绝」，因为那等于把拒绝换个地方。

## 6. 契约变化

| 位置 | 现在 | 改后 |
|---|---|---|
| 00 §5.6 并发闸 | 超限 ⇒ 拒绝 | 超限 ⇒ 入队；拒绝逻辑整段删除 |
| 00 §6 C4 工具 | 并发满返回 409 文本 | 不再有这条错误；描述里删「超了会报并发已满」，改为「提交后自动排队」 |
| 00 §6 C5 路由 | `POST /jobs` 可能 409 | 不再 409；返回的 `JobView.phase` 可能是 `waiting` |
| `route.ts` / `run.ts` | `assertCapacity` | 删除；`assertCapacity` 的测试改成队列测试 |
| `config.ts` | `maxConcurrency` 1..∞ | 1..8（服务端上限 8），默认仍 4 |
| `LovartMeta` | 无 `sessionId` | 加 `sessionId`；`startLovartJobs` 写进去 |
| `GET /jobs`、`GET /jobs/:id`、`DELETE /jobs/:id` | 全局 | 只返回本会话；缺 `sessionId` ⇒ 400 |
| `POST /jobs/:id/confirm` | 无 body | body 带 `sessionId`，不匹配 ⇒ 404（不泄露别的会话有没有这个任务） |
| `JobView` | 派生 `phaseLabel` / `terminal` | 再加派生 `holdsSlot`（来自 `PHASE_TABLE`），供侧栏数 `运行 N/M` |
| `GET /options` | 无容量信息 | 加 `maxConcurrency`，与 `maxCount` / `maxRefs` 同处 |
| `DELETE /jobs/:id` | 只对终态 | **`waiting` 也允许删**（它从没碰上游）；其余非终态仍拒绝 |

`sessionId` 的放法定死一条：**POST 用 body，GET / DELETE 用 query**（`?sessionId=`）。

DELETE 也走 query，是因为部分客户端与代理会丢掉 DELETE 的 body —— 丢了就变成「没有会话」，
删不掉还查不出原因。不引入 header，也不两种都收。

`maxConcurrency` 现在表示「同时提交给上游的任务数」，不是「最多能提几个」。

## 7. skill（必选）

### 7.1 注册方式

`@deepseek-ai/dsh-skill` 暴露 `ctx.skills.register(skill)`，插件在 `apply` 里直接注册，不落文件、不需要 filesystem provider。

```ts
ctx.effect(() => ctx.skills.register({
  name: 'lovart',
  description: '用 Lovart 出图：提交任务、看队列、取图路径',
  whenToUse: '用户说「lovart 作图」、要画图 / 改图 / 以某张图为参考时',
  body: LOVART_SKILL_BODY,   // 纯字符串常量，放 src/host/skill.ts
}))
```

`inject` 增加 `'skills'`（**必选**）：没有 skills 的 profile 里插件不加载。用户已确认接受。

### 7.2 正文大纲（写进 `src/host/skill.ts`）

1. 触发语：「lovart 作图」；用户要画图、改图、拿某张图当参考时用。
2. 开工先看已有的：`job_list` 看本会话任务；`lovart/` 目录看历史图（文件名「时间戳_提示词」）。
3. 提示词写具体（主体、风格、光线、构图）；`ratio` / `size` 只拼进 prompt，不是 API 参数。
4. 一次调用最多 4 个任务，但**提交不会被拒**：超出的自动排队，不用重试、不用等。
5. 提交后不要轮询、不要 sleep，等完成通知。
6. 收到通知：`job_output` 拿路径 → 只告诉用户「生成完了 + 路径」→ 停下。
7. 结果里写明「用户在侧栏自己提交」时，什么都不做。
8. 永远不要替用户确认扣积分。

### 7.3 与工具描述的分工

| 载体 | 回答 |
|---|---|
| skill（常驻 description） | 什么时候用、整体流程、边界 |
| 工具 `description` | 参数怎么填、失败了怎么办 |

两者不重复：skill 决定「要不要用这个插件」，description 决定「用的时候怎么填」。

## 8. AI 的工作台接口

AI 看不见侧栏，只能读工具结果。它需要四件事，按重要性：

1. **一次拿到整张台面**（prompt / 参数 / 队列位次 / 空位），不是 `job_list` 那种壳。
2. **批量提交**：一次调用提交多张**不同提示词**的卡（现在 `count` 只能同提示词多张）。
3. **动作与侧栏对齐**：用户能删的 AI 也能删；用户能取消的 AI 也能取消。
4. **可重试语义**：错误里带「等 / 停 / 去填凭据」，而不是只给一句人话。

### 8.1 现状对照

| 需要 | 现在 | 缺什么 |
|---|---|---|
| 看见台面 | `job_list`：id / kind / label / status / progress / detail / 时间 | prompt、model、ratio、size、refs、files、队列位次、空位 |
| 拿结果 | `job_output`，一次一个 | 20 个任务要 20 次往返 |
| 提交 | `lovart_generate`，`count` 同提示词多张 | 多张不同提示词要 N 次调用 |
| 删除 | 只有侧栏路由，**AI 没有工具** | AI 说「我删了」是假的 |
| 取消 | `job_kill` | 够用 |
| 判断 | 错误文本是给人看的 | 没有「能不能重试」 |

### 8.2 定了：两条工具，一条提交、一条看/删

| 工具 | 只做一件事 | 明确不做 |
|---|---|---|
| `lovart_generate`（已有） | 提交任务；`count` = **同一提示词**多张 | 不读台面、不删除 |
| `lovart_board`（新增） | `snapshot` 看台面、`delete` 删任务 | **不含 submit**；取消仍用 `job_kill` |

```ts
lovart_board({ action: 'snapshot', limit?: number })
  // → {
  //     slots:    { running, max, waiting },
  //     waiting:  [{ jobId, seq, prompt, model, ratio, size, refs, priority }],
  //     active:   [{ jobId, seq, prompt, model, ratio, size, refs, priority, phase, elapsedMs }],
  //     finished: [{ jobId, seq, prompt, phase, files, error? }],   // 含 failed / cancelled
  //   }
  //   每项一行，紧凑；默认最近 10 条 + 汇总计数，不吐全量历史

lovart_board({ action: 'delete', jobId })
  // → { deleted: true }；只对终态；跨会话 ⇒ 404
```

**多张不同提示词不新增批量入口。** `lovart_generate` 是 `isConcurrencySafe: true`，模型在一个 turn 里并行调 N 次即可。这样「提交」只有一条入口（ADR-0005），`lovart_board` 也不会变成第二个提交口。

为什么不把 `submit` 塞进 `lovart_board`：那会让「看台面」的工具同时能写，模型在该看的时候会去提交，而且提交立刻有两条入口。

| 期 | 交付 | 验收 |

| **P3-4 多卡 UI** | ~~4 个输入卡 + 队列状态~~ **暂不做** | 2026-11-08 用户决定：先不建 4 个 table，需要时再说 |
| **P3-5 UI 收口** | 复制按钮、竖排 `⋮` 菜单、focus 态统一到现有语言（§13.4） | 三个新控件与 `.lovart-ghost` / `.lovart-select` 同边框圆角；键盘 Tab 能看见焦点 |
| **P3-6 闭环补口** | 非终态的取消入口（含下载中清理已落盘文件）、确认失败态、凭据常驻入口、重启空态、删除二次确认、`1/4` 序号（§13.7） | 任何阶段都能放弃且不留下半套图；卡在确认能退出；key 填错能回去改；重启后知道图在哪；误点删除要再点一次 |

**P3-0 已于 2026-11-08 落地**：`LovartMeta.sessionId`、`/jobs` 全部按会话过滤、缺 `sessionId` 400、跨会话 404。

**P3-1 已于 2026-11-08 落地**：`waiting` 阶段、`SlotQueue`、`assertCapacity` 删除、`downloading` 改不占槽、`config.maxConcurrency` 上限 8。
两处顺延：① `DELETE` 对 `waiting` 放开要同时取消 job，挪到 P3-6（取消功能一起做）；
② 侧栏的 `运行 N/M` 需要 `JobView.holdsSlot`，随 P3-4 一起加。

**P3-2 已于 2026-11-08 落地**：`src/host/skill.ts`、`inject` 加 `skills`（必选）、`apply` 注册 `lovart` skill；
正文写了触发语、排队不重试、完成后只汇报、侧栏任务不处理、三条红线。

**P3-3 已于 2026-11-08 落地**：`lovart_board`（`snapshot` / `delete`）；快照与删除逻辑在 `job/board.ts`，
路由的 `DELETE` 与工具共用 `removeJob`，不各写一份过滤与 404 规则。
`finished` 取代原计划的 `done` 字段名——它同时包含 failed / cancelled，叫 done 会误导。

**P3-5 / P3-6 已于 2026-11-08 落地**：

- 取消：`POST /jobs/:id/cancel`（工具侧仍是 `job_kill`）；只对非终态开放；
  `waiting` 可删（先取消）；`finishCancelled` 会删掉已落盘的图。
- 侧栏：`⋮` 菜单（复制提示词 / 取消任务 / 删除此任务两步确认）、确认失败换成「取消此任务」、
  顶部常驻「凭据」入口（凭据类错误自动展开）、空态写明历史图在 `lovart/`。
- 任务编号与优先级：卡片前缀显示 `#7`（会话内递增，人和 AI 共用的称呼）；
  `lovart_generate` 支持 `priority: 'high'`，high 插到所有 normal 前面。
  `batchIndex` / `batchSize` / `queuePosition` / 快照 `ahead` 全部删除 ——
  位次每轮轮询都会变，不是身份；「还有几个在等」看 `slots.waiting`。
- UI 收口：复制按钮改白底细边、默认藏起来 hover 出现；`⋮` 竖排；四处 `:focus-visible`。

**P3-4（多卡 UI）按用户决定暂缓**，`JobView.holdsSlot` 因此也没有加——侧栏暂时不显示 `运行 N/M`。

顺序说明：

- **P3-0 先单独修**：它是现存 bug（跨会话串台），与队列无依赖，先修可以先验证。
- **P3-1 必须早于 P3-2**：skill 正文要写「提交即排队」，队列没落地时写这句话就是假的。
- **P3-3 早于 P3-4**：多卡 UI 需要「AI 已经能看见台面」这个前提，否则 4 张卡只是 4 个表单。

## 11. 风险与回退

| 风险 | 处置 |
|---|---|
| 队列把「上游 8 槽」变成「本地无限队列」，用户以为在跑其实在等 | `waiting` 徽章 + 进度行「等待空位」+ 顶部状态条，三处可见 |

### 13.7 闭环缺口（用户问「逻辑闭环了吗」）

顺着用户从装插件到重启的完整路径走了一遍，**没有闭环**，有六个断点。
按「会不会把人卡住」排序：

| # | 场景 | 现在会怎样 | 补口（2026-11-08 已定） |
|---|---|---|---|
| L1 | 用户想放弃一个任务（**任何非终态**） | 侧栏没有入口，只有会话头那个「停止」 | **补**：三点菜单加「取消任务」，对所有非终态开放。**取消 = 用户放弃这个任务，图也不要了**：停止轮询、不下载、已下载的部分删掉 |
| L1b | `waiting` / `confirming` 的取消 | 同样没有入口 | 同上，一并覆盖 |
| L2 | 确认扣积分失败 | `confirmJob` 先置 `confirmCount = 1` 再发请求，失败不回滚；任务停在 `confirming`，按钮仍可点，再点报 409 —— 死锁 | 保持「先置 1」（防双击重复扣费，规范 §5.3）；**失败后按钮换成「取消此任务」**，走 L1 的取消 |
| L3 | DSH 重启 | 侧栏一片空白，图还在 `lovart/`；用户以为图丢了 | 空态文案改成「本会话暂无任务；历史图在 `lovart/` 目录」 |
| L4 | 删任务 | 即时删除、不可恢复；图也一起删（这一点没问题） | **二次确认**：第一次点变「确认删除」，再点才执行 |
| L5 | 凭据填错 | 保存"成功"，直到第一次出图才失败；失败后**没有入口回去改** | **不做测试连接**（假设用户填的一定对）。改为：顶部常驻一个「凭据」入口，随时可重新填；错误属于凭据类（未配置 / 上游 401/403）时自动展开 |
| L6 | 一次出 4 张 | 4 张卡 prompt / 参数全一样，分不清哪张是哪张 | 卡上标 `1/4`、`2/4`（同一次提交的序号），不做分组 |

**L1b 与 L2 是真正会把人卡住的**，其余是体验缺口。

「取消」的语义写死：**用户放弃这个任务，结果不要了。**

- 不是「停止上游」——C1 没有中止端点，上游该跑完还是跑完。这一点必须在 UI 上说清（按钮 title 写「放弃此任务，已生成的部分会删掉；上游可能仍在跑」），否则用户会以为「取消了所以不扣积分」。
- 与「停止」的区别：会话头的停止是 DSH 的 `job_kill`；侧栏的取消是同一套 `cancel()`，但**多一步清理**——已落盘的图要删掉。
- 落到代码：`finishCancelled` 里若 `meta.files` 非空，先 `removeImages(meta.files)` 再结算；`saveImages` 的下载循环里要检查 `cancelled`，不能等 6 张全下完才发现用户跑了。

**DSH 会话头那个「停止」按钮不是我们的，也删不掉。** 它调到同一个 `cancel()`，所以效果必须与侧栏的「取消」完全一致：放弃 + 清理已落盘文件。
它叫「停止」是 DSH 的措辞，实际停不了上游——这个落差只能由我们的文案承担：

- 侧栏**不复制**一个「停止」按钮，只提供「取消」，措辞里不出现「停止」。
- skill 里写明：`job_kill` 等于**放弃**，不是停止；只在确定不要结果时用。
