## 0. 一句话

**一个 DSH 插件：把 Lovart 免费排队出图接进侧边栏和 agent。**

```
agent 说一句话  ──┐
                  ├──→ 同一个任务表 ──→ Lovart ──→ 图落进会话工作区
侧边栏点一下    ──┘
```

## 1. 边界

### 1.1 做

| 能力 | 入口 |
|---|---|
| 提交出图任务 | `lovart_generate` 工具 / 侧边栏输入框 |
| 看任务进度 | 会话头 job 列表（DSH 自带） / 侧边栏图墙 |
| 人工确认扣积分 | **只有侧边栏** |
| 看图 | 侧边栏缩略图 + 灯箱 |
| 图进工作区 | 自动落盘 `<cwd>/lovart/`，文件树/预览/拖进对话全可用 |

### 1.2 不做

| 不做 | 为什么 |
|---|---|
| 断点续跑、`state.jsonl`、文件锁 | 那是挂机跑批工具的需求。插件是即时工具，重启后重发一次更符合直觉 |
| **跨重启**的槽位账、402 熔断、超时释放 | 槽位队列只在内存（§5.6），重启即丢；不做持久化账本，也不做 402 熔断与超时释放 |
| 视频、Chat 模型 | 出图是唯一目标。模型表只放 IMAGE |
| 自动确认 `pending_confirmation` | 会扣积分。**任何代码路径都不许自动确认** |
| 与 Rust 工具互通 | 两个产品，各存各的图 |

### 1.3 已知损失（必须写进 README，不许让用户自己发现）

- **DSH 重启后任务丢失**。已落盘的图还在。
- **排队模式可能要等 30 分钟以上**。这是免费的代价，不是 bug。

## 2. 复用与自建的边界

DSH 已经提供了后台任务能力（`ctx.jobs` / `dsh-tool-jobs` / `dsh-client-ui-jobs` / `dsh-api-job-controller`）。
**这些不构成「凡是现成的就用」的理由，也不构成「凡是自己的就留」的理由 —— 逐项算。**

| 项 | 自建代价 | 复用代价 | 结论 |
|---|---|---|---|
| 生命周期、完成通知、agent 唤醒 | ~200 行，且通知要接 `agent/inbox` 私有机制 | 0 行，DSH 已验证 | **复用** |
| `job_output` / `job_list` / `job_kill` 三条工具 | 3 条工具 + 分页 + 截断 | 0 行 | **复用** |
| 会话头部任务列表（一行文字 + 输出面板） | 一套列表 + 停止控件 | 0 行 | **复用**（但它显示不了图，见下） |
| **侧栏 tab（图墙）** | 必须写 | **无替代**：`dsh-client-ui-jobs` 只画一行文字与终端式输出面板 | **自建** |
| **槽位队列** | ~90 行（`job/queue.ts`） | `maxConcurrentJobsPerOwner` 默认 10，数的是「本 session 的 job 数」，且**满了就拒**；Lovart 槽位是账号级的、要排队 | **自建**（语义不同） |
| `lovart_wait` | ~40 行轮询 | `job_output(wait: true)`，上限 `maxWaitTimeoutMs` 默认 60 万 ms | **复用** |
| `lovart_status` | ~20 行 | `job_list` | **复用** |
| 落盘命名 / 去重 | 必须写 | 无替代 | **自建** |
| `pending_confirmation` 确认 | 必须写 | 无替代：`job_kill` 是杀不是确认 | **自建** |

### 2.1 会话头 job 列表 ≠ 侧栏 tab

两者**不互斥**，用途不同：

| | 会话头（`dsh-client-ui-jobs`） | 侧栏 tab（自建） |
|---|---|---|
| 显示 | `lovart-3f2a… [lovart] running 02:31` | 缩略图网格 |
| 展开 | 终端式输出面板 | 大图灯箱 |
| 能做的 | 停止（`ctx.jobs.kill`） | 提交、确认扣积分、取消（同一条 `kill`）、看图 |
| 谁看 | 想知道 agent 在干什么 | 想看图和收图 |

会话头由 DSH 提供，**我一行都不写**。侧栏 tab 必须自己写，因为图只能画在那里。

## 3. 原语

五个不可再分的构件。其余一切由它们组合。

### P1 · 凭据

```ts
const ACCESS = credentialRef('LOVART_ACCESS_KEY')
const SECRET = credentialRef('LOVART_SECRET_KEY')
```

`ctx.credentials.resolve(ref)` 每次请求前解析一次（不缓存），返回 `{value, source} | undefined`。
未配置 ⇒ 工具直接报错「未配置 Lovart 凭据」，不静默降级。

### P2 · 签名请求

**唯一出网口。** 除它以外，仓库里不允许出现第二个 `fetch`。

```
签名串 = `${METHOD}\n${path}\n${timestamp}`      // path 含 /v1/openapi 前缀
签名   = hex(HMAC-SHA256(secret, 签名串))
```

| Header | 值 |
|---|---|
| `X-Access-Key` | access key |
| `X-Timestamp` | 秒级 Unix 时间戳（**每次请求重算**） |
| `X-Signature` | 上式计算 |
| `X-Signed-Method` | `GET` / `POST` |
| `X-Signed-Path` | 含前缀的完整 path |
| `User-Agent` | `LovartAgentSkill/1.0` |

### P3 · 信封

上游所有响应都是 `{code, data}`：

```ts
if (body.code !== 0) throw new UpstreamError(body.message, body.code)  // 严格 === 0，字符串 "0" 也算错
return body.data ?? body
```

非 2xx 时上游仍返回 `{code, error}` 信封 ⇒ **先解信封拿业务码，再看 HTTP 码**。

### P4 · 任务元数据

**分工，不是重复。**

| 谁 | 存什么 | 存在哪 |
|---|---|---|
| `ctx.jobs` | 生命周期（`running` / `completed` / `failed` / `killed`）、label、progress、detail、起止时间、输出环 | DSH 进程内 |
| **本插件** `Map<JobId, LovartMeta>` | `sessionId` / `prompt` / `threadId` / `projectId` / `model` / `ratio` / `size` / `refs[]` / `phase` / `files[]` / `urls[]` / `confirmCount` | 本插件进程内 |

为什么必须自己存一份：`JobView` 只有 `id / kind / label / status / progress / detail / startedAt / finishedAt / output`。
**它存不下 `files[]`（侧栏要画缩略图）、`threadId`（确认时要发）、`confirmCount`（防重复扣费）。**

反过来，`Map` 也存不下「谁来通知 agent」「谁能 kill」—— 那是 `ctx.jobs` 的。

**两者字段不相交，谁也不是谁的投影。**

### P5 · 落盘

```ts
dir  = join(cwd, 'lovart')
file = join(dir, `${stamp}_${slug(prompt)}.${ext}`)
```

**`cwd` 怎么拿**（顺序固定，不猜）：

1. `await ctx.workingDirectory.ensure(agent, signal)` —— 有 `workingDirectory` 服务时用这个（它会校验目录存在、必要时回落到原始项目）
2. 否则 `ctx.sessions.get(sessionId)?.header.cwd` —— Session header 里的绝对路径（`dsh-session/lib/types/types.d.ts:70`）
3. 都没有 ⇒ **报错**「无法确定会话工作目录」。不落到 `process.cwd()`：那是 DSH 进程的目录，不是用户的会话目录，写进去的东西用户找不到。

同名不同内容 ⇒ `-2`、`-3` 后缀，**不覆盖**。
`slug` 规则：换行/制表→空格、去掉 `\/:*?"<>|`、连续空白→`_`、截断 40 字、空则 `prompt`。

## 4. 数据形状

### 4.1 LovartMeta（本插件持有）

```ts
type JobId = string   // 由 ctx.jobs 发放，`lovart-<16位hex>`

interface LovartMeta {
  jobId: JobId
  /** 归属会话。一个会话 = 一个项目：侧栏与读接口只认本会话（见 §6 C5）。 */
  sessionId: string
  // ── 入参（提交后不可变）
  prompt: string
  model: ModelId
  ratio: string          // `3:4`
  size: '1K' | '2K' | '4K'
  refs: string[]         // 参考图 CDN 地址（已由 /lovart/api/refs 上传）；重跑原样复用
  priority: 'high' | 'normal'   // 本地排队优先级；只影响「谁先占槽」，提交后失效
  seq: number                   // 会话内递增的展示编号（#7）；人和 AI 用它指认任务
  // ── 上游句柄
  threadId?: string
  projectId?: string
  // ── 进度
  phase: Phase
  // ── 结果
  files: string[]        // 本地绝对路径
  urls: string[]         // 上游 CDN 原始地址
  error?: string
  // ── 时间（毫秒）
  createdAt: number
  submittedAt?: number
  settledAt?: number
  // ── 确认闸门
  confirmCount: number          // 已经点过几次确认（防重复扣费）
  /** 唯一非数据字段：唤醒 run() 里停在 confirming 的 await。见 §5.3 */
  unblockConfirm?: () => void
}
```

`jobId` **由 `ctx.jobs.start()` 发放**，本插件不自己造 id。格式是 `<kind>-<16位hex>`，
所以 `kind: 'lovart'` ⇒ `lovart-3f2a1b8c9d0e4f57`。

**`kind` 必须做类型声明合并**，否则 `JobKind` 联合类型里没有 `'lovart'`：

```ts
declare module '@deepseek-ai/dsh-jobs' {
  interface JobKindMap {
    lovart: 'lovart'
  }
}
```

（`dsh-tool-terminal` 就是这么声明 `'pty-send'` 的，见 `dsh-tool-terminal/lib/types/index.d.ts:9`。）

### 4.2 Phase 表

**唯一真源** = `src/host/job/phase.ts` 的 `PHASE_TABLE`。加阶段必须加一行，否则编译不过。

`phase` 是 **Lovart 特有的业务阶段**，与 `ctx.jobs` 的 `JobView.status` 是两个粒度，不是两份真相：

| phase | 含义 | 占槽 | 对应 `JobView.status` | 写进 `job.progress` 的文本 | 侧栏徽章 |
|---|---|---|---|---|---|
| `waiting` | **本地等空位，还没提交上游** | ❌ | `running` | `等待空位` | `等待中` |
| `submitting` | 设模式 + 建项目 + 发 chat | ✅ | `running` | `提交中` | `提交中` |
| `queued` | 上游已收，排队 | ✅ | `running` | `排队中` | `排队中` |
| `generating` | 上游生成中 | ✅ | `running` | `生成中` | `生成中` |
| `confirming` | 上游要人工确认（**会扣积分**） | ❌ | `running` | `等你确认（会扣积分）` | `待确认` |
| `downloading` | 已出图，正在下载 | ❌ | `running` | `下载中` | `下载中` |
| `done` | 已落盘 | ❌ | `completed` | —（`detail` = 文件数） | `已完成` |
| `failed` | 终态失败 | ❌ | `failed` | —（`detail` = 原因） | `已失败` |
| `cancelled` | 人取消（`job_kill` / 侧栏取消） | ❌ | `killed` | — | `已取消` |

每行还有一个 `tone` 字段（`active` / `waiting` / `done` / `idle`），只决定侧栏徽章外观：
`JobView.tone` 直接透传，前端**不按 `phase` 判断**（ADR-0005）。

**四条规则**：

1. **`phase` 推进时同时调 `job.updateProgress(文本)`** —— 会话头的 job 行就显示这一行。这是 `JobView` 唯一能带业务信息的地方。
2. **`waiting` / `confirming` / `downloading` 不占槽**：`waiting` 还没提交，`confirming` 上游在等人，`downloading` 上游已 `done`（本地 IO 不该挡队列）。它们不占槽，否则会互相卡死。
3. **`phase` 到终态时必须同时结算 `ctx.jobs`**（`done` 的 promise resolve 成 `JobOutcome`），否则会话头那一行永远转圈。
   `phase` 只是 `LovartMeta` 上的一个字段，**它自己不会让 job 结束**。
4. **`waiting` 与 `queued` 是两件事**：前者是**本地**没轮到（我们的队列），后者是**上游**排队。两个词不混，徽章也不混。

### 4.3 上游状态 → phase

| 上游 `status` | phase |
|---|---|
| `pending` | `queued` |
| `running` | `generating` |
| `pending_confirmation` | `confirming` |
| `done` | `downloading` → `done` |
| `abort` | `failed` |
| 其它 / 缺失 | `failed`（**不兜底成 generating**） |

> ⚠️ `status` 字段缺失必须报错，不能当成 `generating` 继续轮询 —— 那会永久占着并发。

### 4.4 模型表

只放 IMAGE。字段：`id` / `readableName` / `tool`（结构化路由工具名，可空）/ `quality`（可空）。

| id | 工具名 | 质量 |
|---|---|---|
| `nano-bn-pro` | `generate_image_nano_banana_pro` | — |
| `nano-bn-2` | `generate_image_nano_banana_2` | — |
| `nano-bn-2-lite` | *（空）* | — |
| `gpt-image-2-low/medium/high` | `generate_image_gpt_image_2` | low/medium/high |
| `gpt-image-2.6-sunburst-low/medium` | `generate_image_gpt_image_2_6_sunburst` | low/medium |
| `gpt-image-2.6-flare-low/medium` | `generate_image_gpt_image_2_6_flare` | low/medium |

别名匹配用**子串包含**、按表顺序命中，所以更长的别名必须排在前面（`nano-bn-2-lite` 在 `nano-bn-2` 之前）。

> 上表按人读的顺序排，**不是命中顺序**。命中顺序以 `src/host/lovart/models.ts` 的数组为准：
> `gpt-image-2.6-*` → `gpt-image-2-*` → `nano-bn-2-lite` → `nano-bn-pro` → `nano-bn-2`。
> 照上表顺序改数组会改变匹配结果。

**比例与尺寸**（唯一真源 = `src/host/lovart/models.ts`）：

| 项 | 候选 | 默认 |
|---|---|---|
| `ratio` | `1:1` / `3:4` / `4:3` / `16:9` / `9:16` | `3:4` |
| `size` | `1K` / `2K` / `4K` | `2K` |

上游对模型**不做比例 / 尺寸互斥**，三个下拉互不约束；`ratio` / `size` 只拼进 prompt 文本（见 C1 第 1 条）。
P2 起前端下拉必须从 `GET /lovart/api/options` 派生，不在 `Tab.tsx` 另写一份表。

## 5. 数据流

### 5.1 提交（两条入口，一个出口）

```
agent:  lovart_generate({prompt, model?, ratio?, size?, refs?})
side:   POST /lovart/api/jobs  {sessionId, prompt, model?, ratio?, size?, count?, refs?}
                │
                ▼
        领槽：有空位立即拿，没有就进本地队列（不拒绝）
                │
                ▼
        const id = ctx.jobs.start({ kind:'lovart', owner, label, run(job) {...} })
                │
                └── 立即返回 id ──→ 工具/接口回给调用方
```

**`run()` 是同步函数，必须同步返回 `JobHooks`**（`dsh-jobs/lib/types/types.d.ts:199`）。
真正的异步工作放进一个立即执行的 async IIFE，把它的 promise 塞进 `done`：

```ts
run(job) {
  let cancelled = false
  let unblockConfirm: (() => void) | undefined

  const work = (async (): Promise<JobOutcome> => {
    // ① 排队领槽（§5.6）
    job.updateProgress('等待空位')
    const ticket = queue.take()
    if (!(await ticket.granted) || cancelled) return { status: 'killed' }
    setPhase(job, 'submitting')
    try {
      const creds = await resolveCredentials()     // 缺 ⇒ throw
      await api.setMode(true)                      // ← 每次提交前都做
      const projectId = await api.createProject()
      const threadId  = await api.sendChat({...})
      setPhase(job, 'queued')

      // ② 轮询
      while (!cancelled) {
        const s = await api.getStatus(threadId)
        if (s === 'abort')   return { status: 'failed',    detail: '上游中止' }
        if (s === 'done')    { /* 5s 复核 → result → 下载 */ return { status: 'completed', detail: `N 张` } }
        if (s === 'pending_confirmation') {
          ticket.release()                                        // 等人期间不占槽
          setPhase(job, 'confirming')
          await new Promise<void>(r => { unblockConfirm = r })    // ← 停在这里等人
          unblockConfirm = undefined
          if (cancelled) return { status: 'killed' }
          if (!(await reacquire())) return { status: 'killed' }   // 确认后重新排队
          setPhase(job, 'queued')
        }
        await sleepWithBackoff()
      }
      return { status: 'killed' }
    } finally {
      release()                                                   // 三条路径各还一次
    }
  })()

  return {
    cancel() { cancelled = true; ticket.cancel(); unblockConfirm?.() },
    done: work.catch((e): JobOutcome => ({ status: 'failed', detail: String(e) })),
  }
}
```

**为什么要每次重设排队模式**：`unlimited` 是**账号级持久设置**，随时会被别处（网页端、另一个工具）改回 fast。不重设就会在 fast 模式下扣积分。

**垫图链路（P2）**：

```
浏览器选图或粘贴 → 读成 data URL → POST /lovart/api/refs {name, dataUrl}
  → host 解出字节（png/jpeg/webp/gif，单张 ≤ 10MB）
  → 带签名 multipart（字段名 file）转发 /v1/openapi/file/upload
  → 上游返回 data.url
  → 提交时放进 POST /chat 的 attachments: string[]
```

- **我们只存 CDN URL**（`LovartMeta.refs`），不存 base64；重跑直接复用 URL，不二次上传。
- **单 job 最多 8 张**（`MAX_REFS`）。上游没有硬张数上限，8 对齐参考实现单次粘贴上限。
- `refs` 为空时整个 `attachments` 字段**不下发**：`[]` 与不传是两种语义。
- 任一张上传失败 ⇒ **整批不加入、不提交**；不许静默降级成文生图。
- 浏览器不直连上游、不接触凭据；凭据只在 host 的 `request.ts` 闭包里。

### 5.2 轮询（在 `run()` 的 async IIFE 里）

```
while 未到终态：
    GET /chat/status?thread_id=
        pending               → phase='queued'
        running               → phase='generating'
        pending_confirmation  → phase='confirming'，然后 await 一个 resolver
        abort                 → phase='failed'
        done                  → 等 5s 复核一次（防子任务未起跑误判）
                                 复核仍 done → GET /chat/result → 取 urls → phase='downloading'
```

**退避**：单任务轮询间隔从 10s 起翻倍，封顶 60s。

`JobOutcome.result` 是给模型读的最终文本（文件路径 + 耗时），由 `job_output` **只发一次**。
不放进 `job.append()` —— 那是输出环，会被流式读取消费掉。

### 5.3 确认（只有人能触发）

```
侧边栏点「确认并继续」→ POST /lovart/api/jobs/:id/confirm
    → 校验 meta.phase === 'confirming' 且 confirmCount === 0
    → POST /chat/confirm {thread_id}
    → confirmCount++，唤醒 run() 里的 resolver
```

**resolver 存在 `LovartMeta` 上**（`unblockConfirm?: () => void`），因为路由与 `run()` 是两个执行上下文，
必须有地方能碰到它。这是 `LovartMeta` 里唯一一个**非数据字段**，所以要标出来。

**规则**：

- 一个任务最多确认 **1 次**。`confirmCount >= 1` 时再来一次 ⇒ 拒绝并说明「已确认过一次，再确认会再次扣积分」。
- 确认请求失败**不重试**（可能已在服务端生效，重试 = 重复扣费），且**不唤醒** `run()` —— 让它继续停在 `confirming`。
- **没有 agent 工具能走到这条路径。** 模型永远不能花钱。
- 确认时 `ctx.jobs` 那边的 job **仍在 `running`**（`run()` 还没返回）—— 这正确，它确实在跑。
- 用户取消（`job_kill` 或侧栏取消）时 `cancel()` 会唤醒 resolver，`run()` 看到 `cancelled` 返回 `killed`。

### 5.4 下载

```
GET <url>                       // 裸 GET，不需要 Referer/Cookie（Rust 版已证）
  → 按 Content-Type 定扩展名（image/png|jpeg|webp → .png/.jpg/.webp，兜底 .png）
  → 写 join(cwd,'lovart', name)，同名不同大小加 -N
  → phase='done'
```

**下载中途要能取消**：每张之间问一次 `cancelled`，不能等 6 张全下完才发现用户已经放弃。
取消时已写下的那部分由 `finishCancelled` 删掉 —— 「图不要了」必须真的不留半套。

### 5.5 侧栏读

```
GET /lovart/api/jobs?sessionId=      → JobView[]（只本会话，待确认置顶 + createdAt 倒序）
GET /lovart/api/jobs/:id?sessionId=  → JobView（跨会话 404）
GET /lovart/api/health               → {credentials, credentialsWritable, modelCount, version, webServer}
POST /lovart/api/credentials         → 写凭据（唯一入口，见 §6 C5）
```

侧栏每 2s 拉一次列表。**不做 SSE** —— 任务数量小、刷新频率低，SSE 的连接生命周期管理不值这个复杂度。

> 侧栏只用自己这份 `LovartMeta`，**不读** `ctx.jobs` 的客户端流。两个数据源用途不同（见 §2.1），
> 混读会变成「同一件事两处显示，且迟早不一致」。

### 5.6 槽位队列

```
提交 → phase = waiting → queue.take()
                          ├─ 有空位 ⇒ 立即放行 → phase = submitting
                          └─ 满了   ⇒ 挂着等，前面的任务结算时 release() 唤醒
```

- `config.maxConcurrency`（默认 4，上限 8）是**同时提交给上游的任务数**，不是「最多能提几个」。
- 槽位**全局一份**（账号级），与会话无关；台面按会话分（§6 C5）。
- 占槽判定由 `PHASE_TABLE.holdsSlot` 派生，**不另立计数器**：计数器会与真相漂移。
- `waiting` / `confirming` / `downloading` 都不占槽（§4.2 规则 2）。
- 还槽在 `finally`：成功 / 失败 / 取消三条路径各还一次；重复 `release()` 是空操作。
- 排队中被取消 ⇒ 摘号、`granted` 变 `false`、不占槽、不提交上游。
- 拿到槽位后**立刻再判一次取消**：取消可能刚好发生在放行与醒来之间。
- **优先级**：`priority: 'high'` 会插到所有 `normal` 前面，同优先级内部仍先来后到。
  它只决定「谁先占槽」；一旦提交给上游，上游自己的排队就改不了了。
- **不对外报位次**：位次每 2 秒就可能变，不能当身份用。任务用 `seq`（`#7`）指认，
  进度看 `phase`；「还有几个在等」看快照的 `slots.waiting`，那是汇总不是每张卡的数字。

**不复用 `maxConcurrentJobsPerOwner`**：它默认 10，数的是本 session 的 job 数，
与 Lovart 服务端「最多 8 个并发槽」不是同一件事（见 §2）。

不重投、不算 402。撞上 402 就当普通失败，报给用户看。

## 6. 契约

### C1 · 上游 HTTP

| 端点 | 方法 | 入参 | 出参（`data`） |
|---|---|---|---|
| `/v1/openapi/project/save` | POST | `{project_id:"", canvas:"", project_cover_list:[], pic_count:0, project_type:3}` | `{project_id}` |
| `/v1/openapi/mode/set` | POST | `{unlimited: boolean}` | — |
| `/v1/openapi/mode/query` | POST | `{}` | 模式对象 |
| `/v1/openapi/chat` | POST | `{prompt, project_id, attachments?, tool_config?}` | `{thread_id}` |
| `/v1/openapi/chat/status` | GET | `?thread_id=` | `{status, ...}` |
| `/v1/openapi/chat/result` | GET | `?thread_id=` | `{items:[{artifacts:[{content}], text?}], pending_confirmation?}` |
| `/v1/openapi/chat/confirm` | POST | `{thread_id}` | — |
| `/v1/openapi/file/upload` | POST | `multipart/form-data`，字段名 `file` | `{url}` |

Base URL：`https://lgw.lovart.ai`（可配）。

**五条容易踩的**：

1. **`ratio` / `size` 不是 API 参数。** 它们只出现在 prompt 文本里：
   ```
   resolution: 2K, aspect_ratio: 3:4
   Generate exactly ONE image using the Nano Banana Pro model.
   <user_prompt>
   {原文}
   </user_prompt>
   以上为用户提示词原文，直接使用，请勿修改
   ```
2. **`pending_confirmation` 在 `result` 里是对象**（带花费估算），不是布尔。判定必须用真值检查，用 `=== true` 会漏判 ⇒ 确认闸门被绕过 ⇒ 任务错落成「无产出」。
3. **`tool_config` 只在模型有工具名时下发**：`{prefer_tool_categories: {IMAGE: ["generate_image_xxx"]}}`。空工具名的模型（`nano-bn-2-lite`）**不下发**，否则发的是无效工具名。
4. **`attachments` 只在非空时下发**（URL 数组）。`[]` 与不传是两种语义；垫图必须先过 `/file/upload` 换成 CDN URL，不能塞 base64 或本地路径。
5. **上传也是签名请求**：同一个 HMAC 头，`X-Signed-Path` 为 `/v1/openapi/file/upload`；`Content-Type` 由 `FormData` 自己生成边界，不手写。

### C2 · 插件清单

```json
{
  "name": "dsh-lovart",
  "version": "0.1.0",
  "type": "module",
  "main": "lib/index.js",
  "exports": {
    ".": { "default": "./lib/index.js" },
    "./client": { "default": "./lib/client.js" },
    "./package.json": "./package.json"
  },
  "engines": { "node": ">=22.19", "dsh": ">=0.2.1-rc.1 <0.3.0-0" },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": { "platform": "web" }
  }
}
```

`dsh.client.inject` 只在真用到别的客户端服务时声明。**本插件 client 半边只依赖 better-sidebar 一个**：

```json
"client": { "platform": "web", "inject": ["dsh-better-sidebar"] }
```

> ⚠️ **两个 `inject` 不是一回事，别混**：
>
> | 位置 | 写什么 | 作用 |
> |---|---|---|
> | `package.json` 的 `dsh.client.inject` | **包名**（`dsh-better-sidebar`） | 模块图加载顺序：保证我的 bundle 在它之后加载 |
> | `src/client/index.ts` 的 `export const inject` | **服务名**（`betterSidebar`） | Cordis 服务依赖：保证 `ctx.betterSidebar` 存在 |
>
> 写反了不会报编译错，但运行时会 `cannot get property "betterSidebar" without inject`，
> 而它从渲染路径抛出 ⇒ **整个侧栏面板白屏**。
> 依据：`dsh-better-sidebar/lib/client.js:32800` 的 `inject` 数组里全是服务名（`slots` / `sessions` / `remote` …），
> 而它的 `package.json` 里全是包名。

### C3 · host 半边

```ts
export const name = 'dsh-lovart'
export const inject = ['tools', 'credentials', 'jobs', 'sessions', 'skills']
export function apply(ctx: Context, config: Config): void
```

> **`inject` 只声明必需的四个。** Cordis 的 `Inject` 类型只有「数组」与「名字→拦截配置」两种形态
> （`cordis/lib/types/registry.d.ts:13`），**没有 `{required, optional}` 这种写法**。
> 可选依赖走运行时探测：`ctx.get('webServer')` 在未提供时返回 `undefined`
> （`cordis/lib/types/reflect.d.ts:14`）。

`webServer` 与 `workingDirectory` **不写进 inject**，因为都可选：

- `webServer`：Tauri profile 靠 `@deepseek-ai/dsh-web-app` bundle 间接提供它，换 bundle 就没了。
- `workingDirectory`：用来拿会话 cwd，没有时退回 `ctx.sessions.get(id).header.cwd`（见 P5）。

两者都缺时降级成纯 agent 模式（只注册工具，不注册路由）—— 侧栏读不到数据，但 agent 工具照常可用。
这是可接受的降级，不是静默失败。

`apply` 里做五件事（注册类各套 `ctx.effect`）：

1. 建 `Map<JobId, LovartMeta>`（§4.1）与一份全局 `SlotQueue`（§5.6）—— 都是值，不需要 dispose
2. 注册 `lovart_generate` 与 `lovart_board` 两条工具
3. 注册 `lovart` skill（§6 C7）
4. **`ctx.get('webServer')` 非空才**注册 `/lovart/api` 路由
5. 不需要 sweeper —— 每个 job 在自己的 `run()` 里推进（§5.1）

### C4 · 工具契约

**两条工具，分工写死**（ADR-0005）：

| 工具 | 只做一件事 | 明确不做 |
|---|---|---|
| `lovart_generate` | 提交任务；`count` = **同一提示词**多张 | 不读台面、不删除 |
| `lovart_board` | `snapshot` 看台面、`delete` 删已结束的任务 | **不含 submit**；取消仍用 `job_kill` |

多张**不同**提示词 = 并行调 N 次 `lovart_generate`（`isConcurrencySafe: true`），不新增批量入口。
`lovart_wait` / `lovart_status` 不写 —— 等与查用 DSH 现成的 `job_output` / `job_list`；
台面细节（提示词 / 参数 / 编号 / 优先级）用 `lovart_board`。三者分工见下表（判据见 §2）。

**`lovart_generate`**

```jsonc
{
  "prompt":  "string, 必填",
  "model":   "string, 可选，默认 nano-bn-2",
  "ratio":   "string, 可选，默认 3:4",
  "size":    "enum 1K|2K|4K, 可选，默认 2K",
  "count":   "integer 1..4, 可选，默认 1",
  "refs":    "string[]，可选，最多 8 个 http(s) CDN URL（本地图先经侧栏上传）",
  "priority": "enum high|normal, 可选，默认 normal（high 插到所有普通任务前面）"
}
```

返回：`{ jobs: [{ id, phase, model, ratio, size }] }`

**立即返回，不等图**（理由见 §9.1）。`id` 就是 `ctx.jobs` 发放的 job id，agent 拿它去 `job_output` / `job_list` / `job_kill` / `lovart_board.delete`。

**`lovart_board`**

```jsonc
{
  "action": "snapshot | delete, 必填",
  "limit":  "integer 1..50, 可选，默认 10（snapshot 的 finished 条数）",
  "jobId":  "string, delete 时必填"
}
```

`snapshot` 返回（只读，不发上游请求）：

```
{
  slots:    { running, max, waiting },
  waiting:  [{ jobId, seq, prompt, model, ratio, size, refs, priority }],     // 按派发顺序排，但不报位次
  active:   [{ jobId, seq, prompt, model, ratio, size, refs, priority, phase, elapsedMs }],
  finished: [{ jobId, seq, prompt, phase, files, error? }]                   // 按结束时间倒序，受 limit 限制
}
```

`delete` 返回 `{ deleted: true }`：只对**终态与 `waiting`** 开放（`waiting` 先取消再删），
跑着的返回 409；跨会话 404；连磁盘图片一起删（与 `DELETE /jobs/:id` 同一实现）。

**取消 = 放弃**（侧栏 `POST /jobs/:id/cancel`，工具侧 `job_kill`）：停轮询、不下载、
删掉已落盘的部分。**它不会让上游停下**——C1 没有中止端点，UI 必须写明这一点，
否则用户会以为「取消了就不扣积分」。

**`description` 是给模型的说明书**，必须写清四件事，否则模型不会用对：

1. `count` 是任务数（每个任务一张图）；同时提交给上游的数量有上限，**超出的自动排队，不会报错**；
2. 完成后用 `job_output` 取路径，把「生成完了 + 路径」告诉用户，**然后停下**；
3. 结果里注明「用户在侧栏自己提交」时，**什么都不要做**；
4. 历史图在会话工作目录的 `lovart/` 下，文件名是「时间戳_提示词」；任务记录重启后不保留，图还在。

`isConcurrencySafe: () => true` —— 连提多张是常态，不该串行。

### C5 · 路由契约

前缀 `/lovart/api`，同源，无 token（webserver 默认只绑回环）。

| 方法 | 路径 | Body / Query | 返回 |
|---|---|---|---|
| GET | `/lovart/api/jobs` | `?sessionId=`（**必填**） | `JobView[]`（只含本会话，按下述顺序） |
| POST | `/lovart/api/jobs` | `{sessionId, prompt, model?, ratio?, size?, count?, refs?}`（`sessionId` **必填**） | `{jobs: JobView[]}` |
| GET | `/lovart/api/jobs/:id` | `?sessionId=`（**必填**） | `JobView` |
| DELETE | `/lovart/api/jobs/:id` | `?sessionId=`（**必填**） | `{deleted: true}`（终态或 `waiting`；后者先取消） |
| POST | `/lovart/api/jobs/:id/confirm` | `{sessionId}`（**必填**） | `JobView` |
| POST | `/lovart/api/jobs/:id/cancel` | `{sessionId}`（**必填**） | `JobView`（终态再取消 ⇒ 409） |
| POST | `/lovart/api/refs` | `{name, dataUrl}`（data URL，png/jpeg/webp/gif，单张 ≤ 10MB） | `{url}` |
| POST | `/lovart/api/credentials` | `{accessKey, secretKey}`（两个非空字符串，成对写） | `{configured: true}` |
| GET | `/lovart/api/options` | — | `{models, ratios, sizes, defaults, maxCount, maxRefs}` |
| GET | `/lovart/api/health` | — | `{credentials, credentialsWritable, modelCount, version, webServer}` |

`JobView` = `LovartMeta` + `phaseLabel`（徽章文案，派生自 `PHASE_TABLE.label`）+ `terminal`（是否终态）+ `tone`（徽章外观档位，派生自 `PHASE_TABLE.tone`：`active` / `waiting` / `done` / `idle`）。

**没有位次字段**：`seq` 是身份（`#7`），`phase` 是进度，`slots.waiting` 是汇总；
位次每轮轮询都可能变，放上界面只会让人以为它是身份。

三者都从 `PHASE_TABLE` 派生一次，**前端不按 `phase` 自己判断**（ADR-0005）：新增 phase 时只改表，
前端读 `tone` 即可，不会出现「前端静默落到 active」。

> `tone` 的联合类型在 client 里有一份同名定义（两个 bundle 不能互相 import），
> `readJob` 用 `isPhaseTone` 做运行时校验：取值不合法直接报「后端返回格式不正确」。
> 这是唯一允许的重复点，改 `PHASE_TABLE.tone` 时必须同步它。

**会话作用域。** 一个会话 = 一个项目：所有 `/jobs` 读/写接口都必须带 `sessionId`，缺了直接 400，
**不回落成「全部会话」**。跨会话访问与「不存在」返回同一个 404 —— 不泄露别的会话有没有这个 id。
放法固定：**POST 用 body，GET / DELETE 用 query**（DELETE body 会被部分客户端与代理丢掉）。
两者都是派生字段，不回写 store；前端不自己映射 phase、不自己判断终态。

**图墙顺序只有一种**（`route.ts` 的 `compareTimeline`）：**待确认置顶**，其余按 `createdAt` 倒序。
新任务压在上面，完成的任务不消失、随新任务自然下沉；不做队列、不分页、不切分栏。

`/lovart/api/refs` 是浏览器与上游之间**唯一**的上传代理：路由只拿到字节，凭据与 baseUrl 留在 host。
它不创建任务，也不落盘；成功只返回 CDN URL，失败按统一 `{error}` + 非 2xx 返回。

`DELETE /lovart/api/jobs/:id` 只对终态开放：跑着的任务先 `kill`，否则 `run()` 还在写这份 meta。
删除时连 `<cwd>/lovart/` 里的图片一起删 —— 侧栏删了但文件还在，会变成看不见的残留。
文件已被用户自己删掉也算成功（`rm` 的 `force`），其余错误照常报。

`/lovart/api/credentials` 是**唯一**的写凭据入口：只调 `ctx.credentials.set(ref, value)`，
值落在 DSH 凭据库（`dsh-credentials` 的 `CredentialProvider`）。插件不落盘、不缓存，
每次请求前仍 `resolve` 一次。两个 key 必须成对：缺一个或空白 ⇒ 整单 400，不做部分写入。
`GET /health` 的 `credentialsWritable` 来自 `describe(ref).writable`；为假时侧栏不显示输入框
（填了也存不进去），改由环境变量提供。

`sessionId` 放 **body**，不放 query / header：同一个请求的参数只有一处可读，
避免以后一半在 body、一半在 query；也不让会话 id 落进 URL 与访问日志。

错误一律 `{error: string}` + 非 2xx。**不返回堆栈。**

**没有 `cancel` 路由，也没有列表之外的读接口。** 理由（判据见 §2）：

- 取消 = `ctx.jobs.kill(sessionId, jobId)`，客户端已由 `dsh-api-job-controller` 提供，
  它会调到本插件的 `JobHooks.cancel()`。**自己再开一条路由就是第二个入口。**
- 单个 job 的实时输出 = `ctx.jobs.observe(sessionId, jobId)`，同样是现成的。

本插件只补 DSH 补不了的那部分：**`LovartMeta` 的读写**（`files[]` / `phase` / `threadId` / 确认）。

### C6 · 文件契约

- 目录：`<sessionCwd>/lovart/`
- 命名：`20261108-121530_一只戴帽子的猫.png`
- 冲突：`..._一只戴帽子的猫-2.png`
- **不写任何隐藏状态文件**（没有 `.lovart-state.json`）。`LovartMeta` 只在内存。
- **不写 `state.jsonl`**：没有断点续跑（见 §1.2），重启即丢。
- **删除与取消都会动文件**：删除连文件一起删（终态或 `waiting`）；取消删掉已下载的部分。
  两者都只碰 `meta.files` 里的路径，不按目录扫描。

### C7 · skill 契约

`inject` 含 `skills`（**必选**）：没有 skills 服务的 profile 里插件不加载，而不是加载了却没有开工说明。

| 字段 | 值 | 作用 |
|---|---|---|
| `name` | `lovart` | kebab-case，DSH 技能名语法 |
| `description` | 一句话 | **常驻**，决定「要不要用这个插件」 |
| `whenToUse` | 触发条件 | **常驻**，含触发语「lovart 作图」 |
| `source` | `runtime` | 随插件注册，不落文件 |
| `content` | Markdown 正文 | 按需加载，只写流程与红线 |

正文必须写清六件事，否则模型会用错：

1. 触发语与适用场景；
2. 一次最多 4 个任务、超出的**自动排队**，不要重试；
3. 提交后**不要轮询**，等完成通知；
4. 收到通知后用 `job_output` 拿路径，只汇报「生成完了 + 路径」然后停下；结果里注明「用户在侧栏自己提交」时什么都不做；
5. 指认任务用编号 `seq`（`#7`），**不用位次**；「这张先出」用 `priority: 'high'`（只对 `waiting` 有效）；
6. 红线：不替用户确认扣积分；`job_kill` 是**放弃**不是停止；删除前先跟用户确认。

**skill 与工具描述的分工**：skill 回答「什么时候用、整体流程」，工具 `description` 回答「参数怎么填、失败怎么办」。两者不重复。

## 7. 技术栈

| 项 | 选择 | 为什么 |
|---|---|---|
| 语言 | TypeScript 5.x，`strict` | 上游响应全是 `unknown`，必须逐层窄化 |
| 运行时 | Node ≥ 22.19（DSH 要求） | `fetch` / `crypto.subtle` 都在 |
| 构建 | **tsdown**（rolldown 内核） | 与生态一致；双入口一份配置 |
| 签名 | `node:crypto` 的 `createHmac` | 无依赖 |
| HTTP | 全局 `fetch` | 无依赖 |
| 测试 | `node:test` | 零依赖，够用 |
| UI | React 18（平台模块，不打包） | DSH 外壳已提供 `react` / `react-dom` / `react/jsx-runtime` |
| UI 基础件 | `@deepseek-ai/dsh-client-ui-primitives`（平台模块） | 按钮/菜单/图标与宿主一致 |
| 样式 | **运行时注入 `<style>`** | 避开 DSH 的 CSS-module 构建管线，少一条依赖 |
| 配置 | `@deepseek-ai/schemastery`（DSH 内置） | 设置页自动生成表单 |
| 状态 | 无库。`Map` + `useSyncExternalStore` | 任务量小，引入 zustand 是过度设计 |

**运行时依赖 = 0。** 全部是 Node 内置 + 平台模块。

### 7.1 client bundle 怎么产出

DSH 要求 `lib/client.js` 是这种形状：

```js
window.__ModuleLoader__.load({
  id: 'dsh-lovart',
  factory: (require) => { var module = {exports:{}}; var exports = module.exports;
    /* ...CJS bundle... */
    return module.exports }
})
```

tsdown 配 `format: 'cjs'` + `external: ['react','react-dom','react/jsx-runtime','@deepseek-ai/dsh-client-ui-primitives']`，再用一个 ~30 行的 `renderChunk` 插件把产物包进上面这层。

> 备选：DSH 仓库里有 `externalClientBundle` 适配器（`dsh-tidy-display` 用的就是它），但它需要一个 Harness checkout 路径。**自写包装层，不引外部依赖。**

### 7.2 为什么不用 typert Remote

DSH 的「正统」客户端↔宿主通信是 `@Remote` 装饰器 + 代码生成。本插件只有 9 条路由、单向为主、无流式，用 HTTP 路由是 10 行的事，走 Remote 要引生成器、改构建链。

**判据**：什么时候换？当出现「需要上行流式」或「需要按 Session 作用域鉴权」时。现在都不需要。

## 8. 分层

**不写文件清单。** 要查有哪些文件直接 `ls`；规范只约束「什么代码放哪一层」，不维护一张会过期的目录树。

| 层 | 目录 | 只放什么 | 不许放 |
|---|---|---|---|
| 协议层 | `src/host/lovart/` | 签名、请求、信封、端点、模型、prompt、上游类型 | 生命周期、路由、UI |
| 生命周期层 | `src/host/job/` | phase 表、内存 store、槽位队列、单个 job 的 run、落盘 | 协议细节、HTTP 路由 |
| 装配层 | `src/host/` 根 | apply、配置、错误、DSH 端口、工具、路由 | 业务算法 |
| 侧栏 | `src/client/` | tab、面板、调路由、媒体地址、样式 | 直连上游、拿凭据 |
| 测试 | `test/` | 每个已实现模块一个 `*.test.ts` | 占位测试、渲染测试 |

- 不新增顶层目录；新文件先回答「属于哪一层」，答不出就是分层没想清。
- 加端点只动协议层；加阶段只动 `phase.ts` 的表。

`client/media.ts` 单独一个文件，因为它封的是**本方案唯一的外部依赖**
（`ctx.betterSidebar.hostRouteUrl()` 加 `sidebar/file?sessionId=&path=&cwd=`）——
将来若换回原生侧栏，只改这一个文件。

> 修订（2026-11-08）：依据 `dsh-better-sidebar@0.28.2` 的实际导出，`hostRouteUrl(path)` 在服务上，
> `mediaUrl` 未公开（运行时只导出 `apply` / `inject`）。原句写的「`ctx.betterSidebar` 的 `mediaUrl`」
> 是包内实现，不是公开面；封装点改为 `hostRouteUrl`，参数一律走 `URLSearchParams` 编码。

## 9. 分期

> 分期表与验收清单已移到 [`01-立项与分期-2026-11-08.md`](plan/01-立项与分期-2026-11-08.md)。
> 本节只留一条与工具语义绑定的理由。

### 9.1 为什么 `lovart_generate` 不等图

免费排队模式实测 30 分钟起，最长 90 分钟。工具调用阻塞这么久会有三个问题：

1. 工具超时策略会掐断（`timeoutMs` 是协作式的，掐不断就只是让调用方干等）
2. agent 的一整个 turn 被占死
3. 用户看不到任何进度

**而且不需要等**：`ctx.jobs` 在任务结算时会自动通知 owner agent（忙碌时注入下一步，空闲时开一个 follow-up turn）。
agent 拿到通知后用 `job_output` 取结果即可 —— 这正是后台任务存在的意义。

## 10. 侧栏挂法（已定：`dsh-better-sidebar`）

**决定：挂 `dsh-better-sidebar` 的 `ctx.betterSidebar.registerTab`。**

> 与原生侧栏的逐项对比、以及当时怎么试的，见过程文档。

### 10.2 为什么选 A

**决定性的只有一条：能拿到可直接塞 `<img src>` 的图片 URL。**

> 修订（2026-11-08）：依据 `dsh-better-sidebar@0.28.2` 的实际导出，服务上公开的是
> `hostRouteUrl(path)`，`mediaUrl(scope, path)` 只是包内实现、未导出。本插件在
> `client/media.ts` 用 `ctx.betterSidebar.hostRouteUrl()` 拼
> `sidebar/file?sessionId=&path=&cwd=`（参数一律 `URLSearchParams` 编码）得到同一个地址。

省下的不只是 80 行代码，而是「路径编码 + 会话作用域 + 权限边界」这一整类问题。
这类问题一旦写错，表现是**图不显示且不报错** —— 最难查的一种失败。

原生路线的引导页确实更好看一点，但那个差距不足以抵消上面这条。

### 10.3 代价（必须写进 README 顶部）

**没装 `dsh-better-sidebar` 的用户，装了这个插件会看不到任何东西。**

所以：

1. README 第一行写清楚依赖
2. `client` 半边用 `inject: ['betterSidebar']`，缺失时插件不加载（而不是加载了但空白）
3. `cordis.patch.yml` 里留一行注释，说明这条依赖

> 注意：这里说的「侧栏 tab」**不是** `dsh-client-ui-jobs` 那个会话头列表。
> 后者由 DSH 提供、显示不了图、也不在侧栏 —— 见 §2.1。
